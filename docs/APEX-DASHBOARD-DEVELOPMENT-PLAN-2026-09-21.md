# Apex × OKF 统一 Dashboard 开发方案

日期：2026-09-21。状态：M0–M9 隔离验收已完成；v0.8.0 已于 2026-09-29 切换到生产 Vault，并在 Obsidian 1.13.7 验证 Dashboard、Claudian 与 Engine 加载。本文件保留原始开发范围和验收方案；当前实施与生产证据见[验收台账](APEX-OKF-ACCEPTANCE-LEDGER.md)。关联：[架构提案 v2](APEX-DASHBOARD-INTEGRATION-PROPOSAL-2026-09-21.md)。

本方案最初采用 Apex 2.5.4 / `dc7a7098689485f51a8b6195a691f8acc453b79a` 作为分析基线；后续导入前重新核对了选定 SHA。下文描述当时确定的目标实现与验收要求，完成状态以验收台账和上游基线中的记录为准。

实施状态与逐项证据记录在 [验收台账](APEX-OKF-ACCEPTANCE-LEDGER.md)，锁定的上游来源和更新流程记录在 [Apex 上游基线](upstream/apex-baseline.md)。

## 1. 已确定的产品与范围

交付一个统一 Dashboard：Apex 的布局、主题、网页、日历、媒体与小工具保留；OKF 项目接管正式项目，学习、知识、待处理、订阅和导入以原生分区接入；相关功能共用真实内容、上下文和操作。最终停用并替代当前旧 Dashboard 界面，保留 Engine 与 Claudian 的独立边界。

**账目、打卡、人工阅读、专注等 Apex 小工具继续采用原有格式和服务保存。没有将它们改为 Vault 笔记的阶段，也不为此新增记录契约或同步系统。** 必要修改仅是新插件目录、设置接入、生命周期和已有数据接管。用户以后明确要求将某条记录变成日记/资料时，那是一次显式动作，不是常驻双向同步。

最终保留的主要能力：

| 组别 | 内容 | 交付要求 |
|---|---|---|
| 工作台 | 多工作台、主题、Banner、拖拽、成对分栏、宽高调整、折叠、快捷方式 | OKF 分区与 Apex 分区使用同一套宿主能力 |
| 通用内容 | 网页、笔记集合、无封面笔记、备忘、便利贴、文件夹、数据库、DQL、图片、视频 | 继续可用；涉及 OKF 文件的写入遵守对应契约 |
| 项目与行动 | 项目、日志、决策、资料、任务、日历、Daily | 只有一个正式项目模型；任务不同视图修改同一原文 |
| 学习与知识 | Course、Lesson、Study Guide、Wiki、Wiki Map | 保留关联、原文、人工学习确认与状态提示 |
| 输入与阅读 | Capture、Inbox、文件导入、Feed 来源和历史、Digest、微信读书、书籍阅读 | 保留完整流程；外部内容只有明确保留时进入 OKF |
| 小工具 | 天气、农历、倒计时、年度进度、番茄钟、习惯、记账、相册、音乐、阅读计时 | 原能力与原存储保留，不扩大领域改造范围 |
| 系统能力 | Engine 托管、后台状态、通知、重试、Claudian、原生笔记动作 | 不依赖工作台 pane 或某个分区保持打开 |

## 2. 目标架构的四个边界

### 2.1 界面与宿主

唯一 Plugin 入口负责注册 View、命令、设置和服务。Apex 提供布局/主题/通用交互，`SectionRegistry` 统一列出分区；同一份分区定义提供标题、图标、默认配置、配置校验、迁移、渲染与销毁能力。

导航采用“工作台 → 分区 → 详情”。工作台可以绑定 Project/Course 上下文，分区可以跟随或固定自己的上下文；新建/导入动作显示将使用的上下文，允许用户更改。两个 pane 的当前工作台和滚动位置独立。

### 2.2 OKF 领域内容

直接读模型、轻量本地编辑和 Engine 工作流以具体接口提供。所有界面中同一动作调用同一实现，避免项目卡片、详情、日历、数据库各自写文件。

建议从现有代码提取：

| 当前能力 | 目标接口/模块 | 处理原则 |
|---|---|---|
| `VaultDashboardReader` | `WorkspaceQueries` 下的项目/学习/知识/待处理查询 | 保留关系和筛选语义，逐步拆分缓存与投影，不复制旧整页 View |
| `VaultNoteService` | `ProjectActions`、`CaptureActions`、`DailyActions`、`LearningActions` | 继续本地轻量编辑；复用部署模板与契约 |
| Feed/Import 客户端 | `FeedActions`、`ImportActions` 和共享查询 | 保留协议、判断动作、超时/失败处理及阅读位置 |
| `LocalServiceManager` | Plugin 级 Engine 宿主 | 只启动一次，遵守原有停止和恢复规则 |
| 语义/转换监控 | `OperationNotifications` | 查询权威运行态、去重通知，不创建新的业务状态机 |
| `ClaudianBridgeAdapter` | `AgentActions` | 沿用 v1；具体 Workspace 规则继续来自部署资源 |

不要求先把全部服务改名或搬家；可以先提供接口适配，再随功能迁入拆分。禁止新 View 隐藏加载旧 Plugin 来间接获得服务。

### 2.3 Apex 原生工具

`ApexNativeServices` 是集成边界的统称，可以由少量适配函数实现。Habit、Expense、Reading、Pomodoro、Music 等继续调用原服务；共享必要的插件设置、数据目录和生命周期。

它们不经过 OKF Artifact 编辑策略，也不进入 Engine 领域流程。读书进度不会推导学习完成；小工具记录不会被正式任务扫描器当作任务。

### 2.4 存储与设备能力

- OKF 内容：现行 Vault Markdown/YAML。
- 工作台：Apex Markdown 格式的兼容扩展，保存布局、分区配置、引用和内嵌内容。
- Apex 工具：现有 JSON / 插件数据，路径由宿主提供。
- 设备偏好：插件/本机设置；滚动与选择不污染领域文件。
- Engine 运行态、Originals、Feed cache、索引和凭据：继续在 Vault 外。

设备能力分别检测 Vault、Engine API、Claudian、桌面进程启动、webview 等。保留上游移动布局；只有通过隔离 Node 依赖与设备验收后才开放相应移动发行能力。

## 3. 代码落点和上游接入点

建议将上游按 subtree 导入 `dashboard/apex/`；新产品入口与 OKF 代码在外层 `dashboard/src/`。只有外层构建产物安装到 `okf-workspace-dashboard`，上游源码目录不作为另一个插件加载。

| 位置 | 建议内容 |
|---|---|
| `dashboard/apex/` | 上游源码、样式、验证脚本、许可与通用集成补丁 |
| `dashboard/src/plugin/` | 唯一入口、命令、设置和服务初始化 |
| `dashboard/src/workbench/` | 分区宿主、registry、文档 codec、BoardRepository、详情路由 |
| `dashboard/src/application/` | 具体查询与动作接口、上下文解析、编辑能力路由 |
| `dashboard/src/features/` | Project/Learning/Knowledge/Inbox/Reading 等 UI 与控制器 |
| `dashboard/src/adapters/` | Vault、Engine、Claudian、Apex 原生服务的宿主适配 |
| `engine/workspace/vault/system/` | 需要新增的工作台格式契约和任务规范；不新增小工具记录契约 |
| `tests/fixtures/` | 合成任务语料、迁移样本和跨组件 Vault |
| `docs/upstream/` | 上游 SHA、补丁地图、检查命令和升级记录 |

集中维护六类上游接入点：

1. 宿主初始化：提取可组合初始化接口，替代加载第二个 Plugin。
2. 分区注册：添加菜单、配置、渲染和拖放从同一描述获取能力。
3. 工作台读写：保留未知内容、稳定 ID 和局部更新。
4. 领域操作：任务、Daily、数据库/看板、受管文件创建与移动。
5. 数据与设置路径：替代实际冲突的硬编码插件目录/key；不重写小工具模型。
6. 生命周期与设备：按 Plugin/View/Section 划分持有资源和清理职责。

通用接口有默认上游实现；外围注入 OKF 实现。上游文件不直接依赖 OKF 领域模块。对没有整合需求的成熟小工具不为“接口统一”全面重构。

## 4. 关键开发规格

### 4.1 工作台文档与分区

工作台格式使用独立版本，分区持久 ID 不依赖名称或数组下标。注册表类型在界面显示自然名称，机器标识使用 `workspace-projects` 等；旧 `projects` 保留文件集合语义。

文档模型要保存原始 YAML/Markdown 区段与未知扩展内容。只改标题/尺寸时不重写无关正文；遇到未知分区显示占位并保留配置。按原始区段 ID 关联正文，重名 H2 不串配置。

分区配置只保存声明：对象引用、筛选、显示模式、布局参数；不保存查询结果中的项目状态、Source 正文等副本。对象移动/改名后通过路径解析更新引用；不能无条件小写化路径。

工作台文档实例按文件共享。来自卡片、日历、DQL 的同文件修改经过同一局部写入路径。内存只缓存磁盘事实；重读后校验目标旧值，不能用整份旧快照覆盖外部更新。跨进程竞争单独验证，不把 JS 队列当跨进程锁。

### 4.2 统一动作接口

至少覆盖以下动作族，实际命名可在实现时调整：

| 动作族 | 输入重点 | 返回与反馈 |
|---|---|---|
| Project | 创建、状态、日志、Decision；显式 Project 引用 | 实际文件路径/更新结果；全部项目视图失效 |
| Task | 创建上下文、日期、任务引用、目标勾选值/修改字段 | 原文定位、实际结果；今日/项目/日历同步 |
| Capture/Daily | 文本、显式上下文、明确日期、转存来源 | 目标文件/区域；原内容与失败恢复结果 |
| Learning | Course/Lesson 创建，人工完成/撤销，生成/更新材料 | 文件路径或 Engine operation；完成语义分离 |
| Source/Import | 用途、Course/Project、来源身份、解析选择 | 复用/新建 Source、转换/语义操作 ID |
| Feed | 来源、条目、明确判断、生成时机 | 原有 receipt/Source/operation，不重复建立决定缓存权威 |
| Agent | 明确 prompt/skill、contextPaths、动作模式 | Bridge 接受结果或可恢复错误 |

接口不只返回 `void` 或“已发送”。本地写入返回实际路径；后台动作返回现有 operation/conversion 标识。视图据此显示打开结果、处理中、重试；不把请求接受当作业务完成。

### 4.3 项目规格

项目摘要：封面/图标、标题、状态、下一步、最近进展、任务摘要和相关资料入口。详情：目标、范围、当前状态、任务、日志、决策、资料与学习。视图支持列表、卡片、按合法状态的看板。

Project 保持 `project.md + log.md + decisions/`；前者表达当前状态，log 记录时间事实。Source 以 `uses[]` 关联，Study Guide/Wiki 按现有显式字段关联。项目完成不由任务完成率自动推导。

旧 Apex 笔记集合自动保留，仅调整显示名称；用户显式“转为项目”时创建或选择正式 Project，并保留原关联文件。封面属于对象还是某工作台显示覆盖必须明确，禁止两处独立编辑同一含义。

### 4.4 任务、日历和 Daily 规格

统一任务规范由 Engine 资源定义，Python/TypeScript 使用同一组输入与期望夹具。支持正式 `#task` 与普通清单分类，过滤模板、派生视图、代码/YAML 和来源正文示例；日期字段互不覆盖。重复/循环等上游未确认的高级语义不因 UI 可编辑就宣称全面兼容。

新任务优先用 block ID 定位；旧任务用原行、上下文和原文件行号验证定位，歧义时重读。外部任务用 provider 身份，不与本地文本去重合并。

默认写入：项目上下文写项目人工任务区；全局日历写点击日期的合格 Daily；无日期全局行动写今日 Daily；普通工作台清单留在工作台；滴答任务留在远端。创建 Daily 扩展为指定日期，并统一与已有核心日记配置的映射。

补齐 Apex 原有 Todo 的添加、编辑、排序、嵌套、移动、提醒、完成及归档路径的写入盘点。模板生成的新清单保留原意义；把普通清单提升为正式行动必须明确。跨文件任务移动需要先确认目标写入成功再移除源，保留任务锚点并对可恢复失败测试，不能退化成静默复制后删除。

“移除展示”“删除任务原文”“归档已完成清单”是不同动作。领域查询分区不因用户移走卡片而删除原任务；承载原文的清单可执行明确删除并提供合理恢复。

### 4.5 契约感知的编辑

普通笔记维持通用编辑；受管对象按 artifact 与字段提供能力。Project 状态走枚举动作，Source 身份/用途/配对走 Engine，学习完成走人工确认，受管路径移动走合法迁移能力。无法保证合法的通用拖放可以不接受，但提供明确说明与可用的对象操作。

配置工厂从部署契约读取规则，或由 Engine 源契约确定性生成前端描述并在检查中核验一致性；不在前端手写第二份长期 schema。轻量动作在 API 离线时仍可用。复杂对象如 `uses[]` 不能经过逗号分隔字符串编辑器。

### 4.6 内容工作流

快速记录共享一个入口，可选择 Capture、Daily 或便签并携带显式上下文。转存便签成功后替换为引用；重复请求幂等；失败保留原文。

Inbox 保留待判断、待转换、待生成的真实来源和现有动作；它们是投影或 Engine 状态，不在分区配置中增加新状态机。

Reading 保留来源搜索、分页、各期历史、阅读位置、条目判断和原生 Digest；学习保留 Course/Project/Independent 范围；知识保留 Wiki/Map、未复核、陈旧提示。Source 记录用途，Operation 记录执行进度，产物存在与人工学习完成分别判断。

微信读书和书籍阅读仍由 Apex 管理。用户明确要求保留可访问内容时才进入 Intake；阅读进度、计时、翻完一本书不写 `studied_at`。习惯、账目不参与这些流程。

### 4.7 设置、搜索和反馈

统一设置按实际用途组织：工作台/外观、分区与快捷记录、阅读与订阅、小工具、Engine 与 AI、数据兼容与诊断。Apex 原有设置和 OKF 服务配置都可达，不保留两套相互覆盖的顶层设置保存器。

设置存储可使用版本化命名空间，分别保留 Apex 配置、OKF 连接配置、设备 UI 状态；保存一个范围时保留其他范围和未知字段，避免旧 OKF `saveSettings` 白名单把 Apex 配置清掉。原生服务通过设置适配获取原有字段形状。

搜索提供一个全局入口，复用 Vault 文件搜索和 OKF 检索；索引结果仍是候选，打开实际文件。分区搜索只筛选本分区内容，不因小工具保留 JSON 就额外建立全域数据搜索引擎。

后台只突出可行动异常；正在运行的操作可在活动入口查看。错误通知按操作 ID 去重，分区错误隔离；未保存编辑、展开状态与滚动不能在无关刷新中消失。

## 5. 分阶段开发与验收

按 M0–M9 推进。每阶段完成可复现的产物与验收再进入依赖阶段，代码可以拆成多个可审查提交。完整目标不因阶段划分缩减。

### M0：冻结范围和建立验收台账

工作：记录 Apex SHA、现有 OKF 版本和动作清单；盘点所有命令、View、设置、原生 Digest 入口及小工具；把每项能力标为保留/适配/替换，并指向测试场景。将用户已决定的小工具原存储边界写入有效架构文档。

产物：功能台账、上游来源记录、合成 Vault 场景清单、数据归属更新。现有生产 Vault 不作为测试夹具。

门槛：旧 Dashboard 的所有用户入口都有目标位置；无小工具 Vault 化任务；不存在仅靠旧插件才能提供的最终能力。

### M1：导入上游和建立唯一发行入口

工作：在 `codex/` 分支导入 subtree，保留历史/许可与独立上游验证环境；外层构建一个插件包；接通 Apex 宿主初始化、主题/样式和原生工具服务。正式 ID 沿用 OKF Dashboard，开发验证使用隔离 Vault。

产物：可运行 Apex 基线、明确正式入口、构建/检查命令和 ID/path 清单。

门槛：上游构建与相关脚本通过；Apex 布局、网页、日历、原生工具可运行；不加载第二个 Plugin，也不让旧/新界面同时写生产文件。

### M2：抽取 OKF 服务并统一设置和生命周期

工作：把现有主插件中的查询、笔记动作、Feed/Import、Engine 托管、通知和 Bridge 提供给新入口；迁移设置命名空间和命令；原生 Digest 增强继续注册。

产物：可被新分区调用的服务接口、设置适配、Plugin 级监控与清理。

门槛：未打开 Dashboard 也能从命令创建 Capture/Daily、交接 AI、查看后台结果；多 pane 不重复启动 Engine、不重复通知；无需旧 Plugin 存在。

### M3：工作台存储、最小分区宿主和详情路由

工作：实现稳定 ID、未知内容保留、局部更新、共享 BoardRepository；注册原有分区适配与第一个 Project 分区；工作台上下文、分区尺寸、展开详情和独立 pane 状态接通。先围绕真实 Project 用例实现最小接口，再覆盖其他分区。

产物：版本化工作台格式与迁移、分区 registry、宿主、路由、写入协调。

门槛：同名分区、改名/重排、未知字段/正文、不同 pane 并发修改通过；支持多个相同类型分区；网页不因普通配置保存被整体重载。

### M4：完整 Project 与受管编辑入口

工作：实现项目摘要/详情、创建、状态、日志、Decision、引用；连接课程/资料/学习入口；数据库属性编辑、属性/文件夹看板和“新建笔记”进入对应编辑策略；旧 `projects` 作为笔记集合保留。

产物：正式项目模块、对象操作菜单、契约感知编辑、笔记集合转项目动作。

门槛：所有项目入口修改同一 Project；移动引用不删文件；受管字段/路径不被通用操作破坏；离线可完成允许的轻量编辑。

### M5：Task / Calendar / Daily / Capture 完整融合

工作：定义统一任务规范、共享夹具、日期与身份；对齐 Engine 和前端投影；接入日历、今日、项目、工作台 Todo、DQL；统一指定日期 Daily 和快速记录落点；实现便签转存与失败恢复。

产物：统一任务服务、日期写入、日记工厂、记录入口、跨视图状态同步。

门槛：项目创建任务 → 日历完成 → 项目/今日同步；改变布局不还原完成状态；代码示例不混入；重复文本不误改；任务完成不自动完成项目或学习。

这是第一版可供日常评估的完整融合交付。它应同时保留 Apex 网页和通用工具，证明架构能够承载用户真实工作台。

### M6：Learning / Knowledge / Inbox / Import 完整接入

工作：学习摘要与课程/材料详情、Course/Lesson、人工完成、Wiki/Map、待处理分层、导入选项与关联、后台生成/重试/结果跳转；整合全局 AI 上下文动作。

产物：原生学习/知识/待处理分区与详情、完整导入和资料处理链路。

门槛：同一 Source 多个用途不覆盖；Course/Project/Independent 全部正确；生成与人工完成分离；关闭分区不终止后台操作；原有流程动作无遗漏。

### M7：Reading / Feed 和日常预设

工作：接入来源目录、搜索、分页、最新一期、历史、阅读位置、Digest 原生动作；连接用户明确保留资料的用途选择；提供日常/学习/项目/阅读预设。保留微信读书/书籍计时原服务。

产物：完整阅读体验、统一导航与默认工作台、全局搜索入口。

门槛：历史和位置不丢，条目决定幂等；无动作不产生 Source；读完书不写学习完成；同一内容在不同视图的决定一致。

### M8：原存储兼容和整体体验打磨

工作：接管实际存在的 Apex JSON 原文件，适配硬编码数据目录和设置 key；验证原工具；完成焦点、键盘、触摸、缩放、暗色主题、多 pane、按需刷新、请求失效保护和性能基线。

产物：原格式兼容处理、统一体验、性能与故障恢复报告。

门槛：习惯/账目/阅读记录保留原格式，不生成新 Artifact；JSON 接管不覆盖目标已有数据；音乐/计时器/网页/阅读位置不被无关动作重置。移动能力单独按设备验收，桌面声明不提前放宽。

### M9：全流程验收、部署切换与上游演练

工作：合成 Vault 完整测试、真实 Obsidian 验收、重复迁移/中断/回退测试；更新 release manifest、部署脚本、最低 Obsidian 版本和命令兼容；移除旧 View 实现与过渡适配；演练一次真实上游提交更新。

产物：可发布包、迁移报告、回退步骤、上游升级记录、最终功能台账。

门槛：正式插件独立提供全部既有能力；上游与 OKF 验证均通过；升级后完成关键流程而非仅无 Git 冲突；用户数据/运行态不进入代码仓库。

## 6. 每个开发任务的执行流程

每个任务记录：用户场景 → 当前入口/数据 → 目标行为 → 涉及模块 → 写入与失效范围 → 验收证据。涉及领域格式时先改契约/规范和合成夹具，再改消费者；涉及界面时先复用动作再接 UI。

正常执行顺序：

1. 从 M0 台账领取一条明确的用户场景，识别上游基线与现有实现。
2. 实现服务/适配和 UI，保持当前可工作的其他功能可验证。
3. 对高风险写入、状态一致性和跨模块流程增加有意义测试；样式或简单文案调整不机械增加镜像测试。
4. 运行相应检查，解决失败；同步记录迁移要求和上游补丁位置。
5. 在合成 Vault 完成该场景，记录打开的入口、真正生成/修改的文件和可见结果。
6. 提交可审查的变更，说明用户行为变化、验证和已知边界；更新功能台账。

阶段门槛没有通过时不以截图或“页面已接入”标记完成。后台请求返回成功也不能代替等待实际操作结果。

## 7. 验证与发布要求

| 变化 | 必要验证 |
|---|---|
| Dashboard TypeScript / UI | Vitest、TypeScript 检查、production build；相关 Apex 脚本 |
| Python / 任务投影 / 应用工作流 | targeted pytest、Ruff、Pyright |
| 任务语义 / 契约 / 跨组件动作 | Python/TS 共用夹具、fixture-Vault 集成测试、根检查 |
| Claudian 协议或 Provider | 最近 scoped AGENTS.md、typecheck、lint、相关测试和 build |
| 工作台写入 / 迁移 | 未知字段、自由正文、同名 ID、重复迁移、并发、失败恢复和原文保留 |
| 最终版本 | `scripts/check.ps1`、`scripts/build.ps1`、合成 Vault 全流程、真实 Obsidian 操作 |

真实 Obsidian 必测：两个 pane、外部编辑后保存、关闭最后一个工作台、插件重载、Engine 不可用、Claudian 未启用、登录型网页、音乐/计时器、中文主题与窄窗。测试桩中的 mobile/webview 验证不能当作设备真实验收。

以合成 1k/10k 笔记和多个混合分区测冷启动、增量更新、文件读取次数与内存。以实测基线设置回归阈值，不在方案阶段虚构耗时承诺。

## 8. 数据接管、切换和回退流程

1. 读取实际存在的旧 OKF 设置、Apex 工作台与原 JSON；无旧 Apex 数据时跳过对应步骤。
2. 输出将创建/修改的文件与配置映射；只对工作台格式做必要扩展迁移，小工具保持原格式。
3. 保存切换前源文件和版本信息，执行可恢复转换；对已存在的目标文件做冲突检查。
4. 校验工作台内嵌正文、对象引用、Feed 阅读位置、小工具记录及部署路径。
5. 只启用最终 Dashboard 对目标文件继续写入，旧界面退出运行。
6. 完成关键流程，记录结果；若回退，依据变更清单保留切换后的新增内容，不能整库覆盖掉新数据。

Source/Project 原文件默认无需搬迁。JSON 路径接管不变更格式、不同时写旧/新目录；更换 Electron session 分区可能需要重新登录，独立验证，不把 cookie 导入写成通用配置复制。

新格式工作台不能重新交给原版 Apex 保存，直到兼容性经过明确验证；原版可能丢失新增字段。回退使用切换前工作台版本或经过验证的反向转换。

## 9. 上游更新流程

记录上游版本与 SHA → 创建候选分支 → fetch/比较上游变化 → subtree 合并 → 按接入点解决冲突 → 原生脚本与 OKF 场景验证 → 真实 Obsidian 关键流程 → 更新补丁地图与兼容版本 → 生成发布包。

逐项审查主题/网页、任务日期、Daily 落点、工作台序列化、数据库编辑、数据路径和生命周期变化。以功能结果判断是否吸收某个更新，不能把上游旧项目模型覆盖回正式 Project。保留上游能力不要求跟随每次发布立即更新。

当前没有下一版本可用时，可以在独立验证分支中选一个较早的真实上游基线演练合入已存在的新提交，保持正式锁定基线可追踪；不把等待未来上游发布作为切换阻塞条件。

## 10. 最终完成定义

最终版本必须同时满足：一个插件与一致导航；Apex 既有能力保留；正式项目唯一；任务/日历/记录一致；完整学习/知识/资料/Feed 流程可达；后台与 AI 全局可用；Apex 小工具继续原存储；工作台编辑可靠；数据接管可恢复；停用旧 Dashboard 后全部功能继续工作；有一次可复现的上游合并演练。

本次只完成架构与开发计划文档修订。没有执行源码合并、契约变更、构建部署或生产数据迁移。
